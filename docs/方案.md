# 抽帧实验台第一版方案

## 目标

在服务器运行一个 Python 服务，本地浏览器上传 XLSX 清单、发起批跑、查看历史结果。对每个视频，既能看最终图片，也能逐步查看哪些图片被留下、哪些图片被丢弃，以及具体原因。

本项目是临时实验工具：输入和抽帧前处理与 auto_eval_agent 一致；一条命令启动、结果直接保存在项目目录。当前先关注抽帧效果。定稿后迁回允许少量适配，届时去掉过程图片和淘汰记录，恢复原项目正常的抽帧输出。

## 初版实现状态

已实现输入导入、勾选批跑、逐题状态、七步查看、保留/丢弃筛选、单图处理经过与相关图片、原视频定位、新建重跑与文件保存。另已固定 base，支持选择 base 或当前实验版，并按题并排对比两次运行的最终与各阶段结果。启动与实际使用见 README。

本文中的停止在途任务和最终迁回检查属于后续事项，不为这些事项延后真实样本的抽帧效果验证。

第一版先复刻任务类录屏的现有抽帧结果，不调用裁判模型。垂域视觉配置后续独立增加，避免把不同用途混成同一个基准。

## 使用过程

1. 上传 XLSX，预览题目、视频地址和时间范围；错误行就地提示。
2. 给本次运行命名，选择抽帧版本；确认有效行后开始。
3. 批跑时查看每题进度、失败原因和各步图片数量；已完成题可立即打开。
4. 打开单题，按时间查看各步画面；可以只看本步丢弃的图片。
5. 点击任何图片，查看大图、原视频对应位置、处理经过，以及相关比较图片。
6. 修改方法后创建一次新运行，保留旧结果，用相同题目对比。

批次列表用于找问题，单题详情用于解释问题；不在批次首页一次加载全部原图。

## 输入与抽帧前处理

直接复制或参考 auto_eval_agent 已有链路，不要求用户改表格，不另设字段、必填条件、工作表选择方式或时间处理规则。

- `table_dataset.py::convert_table`：表格读取、工作表选择、现有列名识别与字段整理。
- `web/parse_input.py::parse_jsonl`：转换后的任务类输入校验，保留原字段、警告与错误语义。
- `web/operation_media.py`：视频路径、时间范围与抽帧准备；沿用时间超界的原有处理和警告。
- `web/remote_video.py`：远程视频获取方式。

实验工具的本地路径处理做一处适配：服务器上的绝对视频路径直接读取，不沿用目录白名单；相对路径可使用项目目录、`../` 或 OPERATION_VIDEO_ROOTS 指定的查找目录。表格和时间处理不受影响。

迁移这些能力时只带上必要依赖与配置，不依赖旁边 auto_eval_agent 的绝对路径或正在运行的服务。不为满足导入而引入模型客户端、评估标准或后续评估流程。

同一张原始 XLSX 在两个项目中，应得到相同的有效样本、任务字段、选定工作表、警告和错误；只允许运行目录等环境路径不同。重复编号、缺失字段、空值等均按原逻辑处理，实验台可另设内部行编号用于查看，不改写原输入。

抽帧完成后即进入结果查看，不继续分类、模型评估、打分等流程。原字段可作为人工查看的背景信息保留，不用于新增业务判断。

## 每一步怎么展示

真实流程中，末帧会分支保留，任务结束帧也可能在后面补回。记录应跟随实际执行过程，不能假设所有帧都只会一路减少。

| 查看步骤 | 用户看到什么 |
|---|---|
| 最初收集 | 沿途采样、明显变化、首尾和指定结束位置的全部候选画面，以及各自来源 |
| 合并相近时刻 | 同一组有哪些画面，最后选了哪张，其他画面为什么被合并 |
| 确定任务范围 | 哪些画面超出判断出的任务范围；判断依据和保留的末帧 |
| 合并重复页面 | 页面被分成哪些段；每段哪些画面被选中，哪些没选中 |
| 控制图片数量 | 哪些画面受到保护，哪些因数量预算被排除 |
| 最后去重 | 哪些相似图片合并了，最终由哪张代表 |
| 最终结果 | 按时间排列的最终图片，可与上一步、原视频对照 |

每一步显示输入数、输出数、本步丢弃数；候选尚未进入某个步骤时标记“未参与”，不能显示为本步丢弃。

## 一张图片的处理经过

例如，某题出现了一张“保存成功”的图片：

> 在 18.2 秒发现画面变化 → 进入候选 → 相近时刻合并时与 18.0 秒图片归为一组 → 按原方法优先保留 18.0 秒图片 → 此图未继续参与后续步骤。

页面必须同时展示这两张图，允许用户判断：被删的图片是否真的重复，还是恰好包含重要结果。

每个候选自生成起有固定编号。即使时间相同、画面相同，只要来源不同，也保留各自身份。最终另记输出序号，避免把“第几张输出图”误当成全过程编号。

记录至少包括：

- 视频时间、候选来源、图片文件；
- 每一步是否进入、是否选中、是否作为特殊帧补回；
- 原因，例如“相近时刻选择了另一张”“同一页面内没有选为代表”“超出判断的结束位置”“数量预算不足”“最后判为相似”；
- 比较对象或所属图片组，以及决定保留另一张的依据；
- 实际用到的差异数值、规则与本次配置，供展开查看。

有些步骤比较的是一组画面或时间距离，不能硬写成“与某一张图重复”。失败的解码尝试记录为“尝试取图失败”，不伪造图片。

“没有抽到”与“抽到后丢弃”要分开：不在任何候选中的视频时刻，不会有淘汰记录。原视频可以定位查看；手动查看某时刻时，明确标记为人工查看，不混入原始抽帧结果。

## 原样复刻与后续修改

固定原始源码副本、版本、完整配置、输入时间范围和视频文件校验值。运行时记录实际 FFmpeg 版本，保证比较条件可追溯。

固定 base 位于 videosample/versions/base_media.py，实验版本位于 videosample/media.py。base 的方法和默认参数对应复制时 auto_eval_agent 45dd11a 的 hybrid-state-v3.2.0；实验阶段只增加过程记录。每次运行保存实际实现代码及校验值、默认配置和逐题实际配置，不随日后代码修改覆盖旧结果。

第一版先给原始逻辑增加记录，不改变决策，包括当前已发现的边界问题。不能一边做过程查看，一边静默修复原始方法，否则无法确定差异来自哪里。

验证方法：相同视频、配置和 FFmpeg 下，原始副本与增加记录的版本，最终图片数量、顺序、时间、来源、保留原因和图片内容保持一致。原始副本只用于核对，不依赖旁边 auto_eval_agent 的运行环境或导入路径。

## 效果定稿后迁回 auto_eval_agent

实际使用的抽帧实现保持为独立的 `media.py`，对应 auto_eval_agent 的 `src/auto_eval/media.py`。实验台直接调用这个文件；不维护一套仅供演示、之后还需重写的抽帧实现。

- 尽量保持现有函数名、配置类与默认调用方式；迁回时允许少量适配。
- 返回值仍是按时间排序的图片路径列表，沿用 `kf_*.jpg` 和 `keyframes.json` 的既有格式与字段含义。
- 实验期间记录全部候选图片与各步决定；最终迁回时移除这部分记录能力与所有额外中间输出，不只是默认关闭。
- 最终只保留抽帧本身需要的代码和正常输出，不引入实验台专属包。
- 网页、Excel 导入、批跑管理、原视频预览与两次运行对比放在模块外，不搬回 auto_eval_agent。
- 定稿时更新算法版本，使原项目能够识别抽帧方法变化并按已有机制更新缓存。

最终迁回时再做必要的适配与检查。当前先用实验台验证关键画面是否遗漏、重复画面是否过多、任务过程与结果是否容易看懂；其他工程事项不作为当前工作的重点。

## 历史与比较

每次批跑生成独立记录，保存输入清单、算法版本、配置、视频校验值与全部过程结果，不覆盖上一次运行。

“重新跑”创建新记录，旧结果留在各自目录。重试可直接新建一次运行并选取失败项，不设计复杂的尝试管理。服务重启后可从结果文件查看已完成项，未完成项标记为中断；不做自动续跑。

比较时不仅按样本编号匹配，还需核对视频内容与时间范围。相同 URL 可能更新内容，无法证明视频相同的结果明确提示。

第一版支持选择两次运行，对齐同一题，左右看最终画面与各步数量。后续再增加批量差异筛选和人工标记“漏掉结果”“重复太多”“结束偏早”。

## 服务与存储

FastAPI 同时提供网页、上传、批跑与图片查看。安装依赖后用一条命令启动，拟定入口为 `python app.py --host 0.0.0.0 --port 8503`；此处是实现约定，当前尚无可运行入口。使用 Python 时遵守项目约定，使用 moto 环境。

不引入数据库、外部任务队列、独立前端构建或系统服务安装。进度在进程内维护，必要记录用 JSON 保存；清单、视频、候选图和逐步结果统一放在项目 `runs/` 下。删除整个项目即可一并删除实验数据。

按单题调度、有界并发；下载和抽帧分别限制。一题失败不影响其他题。停止运行后不再接收新题，并管理正在运行的 FFmpeg，避免页面显示停止后仍持续占资源。

先保存完整过程记录与候选图，再清理计算临时文件。缩略图按需加载；相同候选被多步引用时不重复复制图片。不做独立的磁盘管理或自动清理功能；测试过程中保留被丢弃的候选图。

为支持原视频对照，下载的视频保存在本项目的运行目录，测试期间保留。用户原有的服务器本地视频仍在原位置读取，不自动删除。路径与下载行为参考 auto_eval_agent，下载链接和文件内容不进入普通日志。

说明文档只需写清安装依赖、启动命令、浏览器地址与结果目录；不另设计部署平台、账户系统或权限管理。使用现有 XLSX 即可。

## 第一版验收案例

1. 同一张现有 XLSX 在两个项目中的输入处理结果一致；坏行沿用原逻辑，坏视频单题报错。
2. 单题最终结果与原始抽帧副本一致，过程记录不改变结果。
3. 能找到某张被丢弃的候选图，并看到实际原因及比较画面。
4. 任务范围、时间合并、页面合并、数量限制和最后去重均有可检查案例；特殊帧后续补回的过程有记录。
5. 短暂成功提示、局部开关变化、长时间停留、显式结束、多轮视频和高频采样均能回放检查。已知缺陷在原始版本忠实呈现。
6. 重启后能查看完成结果，并识别中断任务；重跑保留旧结果。
7. 远程视频不可达、下载中断、FFmpeg 失败与停止任务均有明确状态。
8. 同一批输入跑两个版本，可以对齐查看；视频变化时不会冒充同条件对比。
9. 效果定稿后迁回 auto_eval_agent，允许少量适配，移除过程记录与额外中间输出；此项在后续迁回阶段验证。

## 实施顺序

1. 复制现有输入及视频准备逻辑，原样移植抽帧模块并核对结果。
2. 候选固定编号、逐步记录、候选图片保留。
3. XLSX 导入、后台批跑、历史保存。
4. 批次总览、单题逐步画廊、图片处理经过与原视频对照。
5. 一条命令启动与简短使用说明，先交付真实样本试跑；左右对比等后续按需要补充。

初版跑通后，即可逐项修改抽帧方法，用同批视频比较收益和遗漏；无需等所有后续工具能力完成。
